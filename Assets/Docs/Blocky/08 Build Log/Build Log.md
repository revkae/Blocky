## 2026-09-24 (2D) — 2D scenes, and "turn left" turns left
User request: "2D scenes". Design in [[09 Decisions/Decisions#ADR-038 — 2D is a per-object motion plane, and picking and contacts speak both physics engines|ADR-038]].

- **Motion plane per object** (`BlockyPlane`, `ObjectProgramRunner.Motion`): sprites and objects with 2D physics move along X and turn around Z; `point towards` aims X. The runner can overrule *Auto* for a 2.5D game.
- **Bug fixed:** `turn left` turned right in 3D (a positive yaw is a right turn in Unity), and a test had pinned it. Left is now left in 3D and anticlockwise in 2D. The demo's square walker goes the other way round.
- **Picking** (`BlockyPicking`): 3D raycast, 2D ray intersection, or the topmost sprite under the point with no collider at all — for choosing an object in the editor and for `when clicked`.
- **Contacts:** the relay handles `OnCollisionEnter2D` / `OnTriggerEnter2D` and their exits, and no longer forces a 3D collider onto sprites; `TriggerBroker.OnCollided` carries the other object instead of a 3D `Collision` (signature change).
- **Looks and Reset:** sprites are tinted through `SpriteRenderer.color`; Reset puts the tint and a `Rigidbody2D`'s motion back; speech bubbles draw above sprites.
- **`BLOCKY_PHYSICS2D`:** the 2D physics code compiles only when the project has Unity's 2D physics module (a `versionDefines` entry); Blocky.Runtime was compiled both with and without it.
- **Verified outside Unity only:** 7 `TwoDTests` (planes, sprite motion and turns, the 3D right turn, point towards, tint and Reset, a tagged bump reaching `when collided`) and the corrected turn test pass; the rest unchanged. **Not verified:** picking and real 2D physics messages need a 2D scene in Unity.

## 2026-09-24 (custom blocks) — My Blocks: define, run, inputs, recursion
User request: "Custom blocks, which are already designed in ADR-029". Design in [[09 Decisions/Decisions#ADR-029|ADR-029]], now accepted with an **As built** list; catalog in [[06 Block Catalog/Block Catalog#My Blocks|Block Catalog]]; the VM side in [[04 Runtime/Runtime VM|Runtime VM]]. Catalog now at **85 blocks** (37 steps, 16 conditions, 23 reporters, 9 triggers).

- **VM:** a call is a frame (`Frame.IsCall`) into the definition's script; `Step` returns from it itself (`VmThread.ReturnFromCall`), because with recursion the `run` op can't tell a return from a new call. Threads end at `EndPc` — the definition's exit while inside one. Inputs live on a per-thread array made on the first call. Recursion waits one frame per level, as in Scratch; loops and calls nest up to 256 deep (was 16 for loops), with the frame array growing on demand. Step back saves and restores calls and their inputs.
- **Compiler:** `CompiledProgram.ProcedureNames` / `TryFindProcedure` — definitions by trimmed, case-insensitive name, the first of a name winning. The runner never starts a `define` script, not even on Step ▶.
- **Palette:** a ready-made `run [name]` for each `define` on the object, rebuilt when the names change (`PaletteDragManipulator` and `BlockPrototype` take a prepared node).
- **Advice:** a nameless or duplicate `define`, an unknown or empty `run` name, an `input` block outside a definition — each in English and Türkçe.
- **Bug fixed on the way:** an empty script (a hat with nothing under it) had the same entry pc as the script after it, and `ExitPcFor` gave that script the empty one's length, so it never ran. Empty scripts now get no entry point. Found by reading, proven by a test that failed before the fix.
- **Words:** 248 strings per language now.
- **Verified outside Unity only:** every assembly compiles; 16 new runtime tests (calls, inputs, recursion, the depth limit, Step back, the runner never starting a definition), 12 compile and advice tests and the empty-script test pass, and nothing else changed (the same 4 stand-in gaps). A mutation run — the call return and the moved bound switched off — failed 12 of the 16 runtime tests, so they test what they claim. ## 2026-09-24 (later) — Release fixes: saved programs run at startup, safe save files, link.xml, the demo in the build, an automatic ticker, a quiet analyzer
User request: "Fix what is known to be wrong. Do these all" — section 2 of [[11 Release/Release Readiness|Release Readiness]], written the same day from a code review. Design in [[09 Decisions/Decisions#ADR-031|ADR-031]] (saves) and [[09 Decisions/Decisions#ADR-032|ADR-032]] (the analyzer).

- **Saved programs run the next time the game starts.** Before, only the in-game editor read a save back — so an object ran its scene program while the editor showed the student's, and an object first programmed in the game ran nothing at all. Now `ObjectProgramRunner` looks for its object's save on its first `Initialize` (`LoadProgram`) and makes it its program asset (a clone copies the asset, so it runs the same program); `BlockyRuntimeTicker.Awake` gives a runner back to every saved object without one (`AttachToSavedObjects`); the editor opens `_runner.LoadProgram()`, so what it shows is what runs. A program handed over by code (`SetProgramAsset`: the editor's hot reload, tests, the Editor window) wins over a save.
- **`RuntimeProgramStorage` rewritten.** Key = scene + hierarchy path, `[n]` for same-named siblings (case-insensitive), every part through `SafeName` (escapes `<>:"/\|?*%[]`, control characters, a trailing dot or space and Windows device names; cuts very long names with an FNV hash). `TryLoad` renames an unreadable or newer-version file to `….unreadable` instead of letting the next save overwrite it; `TrySave` never throws. The in-game editor shows either problem above the advice (`storage.unreadable`, `storage.save_failed`, in both language files — 224 strings each now). A `RootOverride` test seam, reset every Play session.
- **`Blocky › In-Game Saves › Show Folder / Delete All…`** in the Editor, because a save now wins over the scene program in the Editor's Play mode too.
- **`Assets/Scripts/link.xml`** keeps `Blocky.Runtime` (reflection-made ops) and `Blocky.Data` (Newtonsoft) at every stripping level — TDD §14's IL2CPP risk.
- **Build Settings:** `BlockyDemo` replaces the URP template's `SampleScene`.
- **No ticker, no silence:** `BlockyRuntimeTicker.EnsureExists()` — called by every runner's `Initialize` in Play mode and by the in-game editor's `Awake` — adds one on a new *Blocky Runtime* object when no scene has one, and logs that it did.
- **`UAL0010` / `UAL0013`:** a pragma and a one-line reason at the top of each of the 18 non-test files with static state, instead of `[NoAutoStaticsCleanup]`, which would break older Unity versions. `BlockyInput`'s two statics were the one set never reset between Play sessions; they are now.
- **Player Settings:** company `revkae`, app id `com.revkae.blocky` (were `DefaultCompany` and the URP template's ids). The Editor's own save folder moves with the company name, so saves made before today are no longer read — they were test data.
- [[Home]] brought up to date (status, build order, known gaps); [[08 Build Log/Demo Scene|Demo Scene]] and [[01 Architecture/Architecture Overview|Architecture Overview]] describe the saves.
- **Verified — outside Unity only.** There was no Unity editor. A C# compiler (Roslyn 4.0.1 on .NET Core 3.1) was assembled from PyPI and NuGet, and Blocky's assemblies were compiled at C# 9 against .NET Standard 2.1 and hand-written stand-ins for the Unity APIs they use: `Blocky.Data`, `Blocky.Localization`, `Blocky.Compiler`, `Blocky.Runtime`, all of `Blocky.Runtime.Tests` and the new Editor menu build with no errors and no warnings. The in-game panel's new lines that call Blocky were compiled on their own the same way; every changed file parses with Roslyn.

Still to see in Unity: a clean compile and console, the full EditMode suite, edit → quit → restart running the edited program, a scene with its ticker deleted still running, the save notice under the table, and a WebGL build at High stripping. ## 2026-09-18 (seventh) — Sound, generated rather than imported
Same user request, seventh pass. Catalog now at **71 blocks** (31 steps, 15 conditions, 17 reporters, 8 triggers).

- **There is not a single audio file in this project**, so a "play sound [name]" block on its own would be a block that does nothing a learner can hear. `BlockyAudio` **generates** its notes instead: a sine wave written into an `AudioClip` at the right pitch and length, with a 10 ms fade at each end so the start and stop are not clicks. MIDI numbering, as in Scratch — 60 is middle C, 69 is A at 440 Hz. Clips are cached per (note, length), because a tune plays the same handful over and over.
- **Four blocks:** `Play Note (note) for (beats)` — holds the script while it sounds, so a column of them is a tune and not a chord; `Play Sound [name]` — loads from `Resources/Sounds/` and carries straight on so sounds overlap, and is silence (not an error) when nothing matches, which is the case for every name today; `Stop All Sounds`; `Set Volume (percent)`. Each object gets one `AudioSource`, added the first time it makes a sound, and it is **2D on purpose**: a first beep that is inaudible because the object sits behind the camera teaches the wrong lesson about one's code. `Stop` silences everything, as it clears clones and bubbles.
- **Verified:**
  - Compiles clean; **9/9 new `SoundTests` pass** — note-to-hertz (A = 440, an octave doubles), a clip of the right length and sample rate on the object's own speaker, the same note reusing one clip, the fade in and out with a real signal in between, one speaker per object however many sounds, volume as a clamped percentage, an unmatched clip name being silence, `stop all` silencing a live source, and `play note` holding the script for its beats and then carrying on.
  - **In Play mode:** a three-note tune (C, E, G) compiled with no diagnostics and ran to completion — the source ended holding `BlockyNote67_35280`, the third note, which is only reachable by playing the first two first. `AudioSource.isPlaying` reads **true in the same frame `Play()` runs**.
- **Not verified — and cannot be from here: whether it is audible.** The editor was unfocused for these checks (and the Game view's Mute Audio toggle may be on), so between one command and the next the audio system suspends and `isPlaying` reads false. What is proven is that the right clip is generated and playback starts; that it comes out of the speakers is for a person with the editor focused.
- **The full suite was not re-run after this pass** — see the note below; `run_tests` was requested while the editor was in Play mode and wedged it again. Sound's own tests were run and passed *before* that, with play mode stopped. The last full run was 286/286 in the previous pass.
- **Process rule, now written down in [[07 Testing/Testing Strategy|Testing Strategy]] after making the same mistake twice:** always `editor_stop` → `recompile` → `run_tests`, and only then `editor_play`. An EditMode run started during Play mode hangs the editor for an hour and every other command with it.

## 2026-09-18 (fifth) — Clones
Same user request, fifth pass. Design in [[09 Decisions/Decisions#ADR-026|ADR-026]]. Catalog now at **66 blocks** (26 steps, 15 conditions, 17 reporters, 8 triggers).

- **Three blocks:** `Create Clone Of [object]` (default `me`), the `When I Start As A Clone` hat, and the cap block `Delete This Clone`. A clone is a plain `Instantiate`, so it carries its colliders, renderer and `ObjectProgramRunner` with it and the VM needs no special case; a `BlockyClone` marker is the only addition, and it exists so `delete this clone` can refuse to delete the original.
- **Capped at 100**, with `Stop` deleting every clone. Past the cap `create clone` quietly does nothing — `repeat forever { create clone }` is a program a learner writes on purpose, and it should slow down rather than take the machine with it.
- **The bug Play mode found, and the unit tests could not.** The first version deactivated the original for the instant of the copy, to keep the clone quiet until it was marked. But disabling an object runs `OnDisable` → `Shutdown()` → every thread it started is halted — so an object cloning *itself* killed the loop doing the cloning: `repeat 3 { create clone of me }` made **one** clone. The test cloned once, where a dead thread changed nothing. Fixed by not deactivating at all (`Instantiate` returns long before the scheduler ticks again), and a regression test now asserts the block *after* `create clone` still runs.
- **`ObjectProgramRunner.Initialize` is now idempotent**, with `Shutdown` clearing the flag. A clone is initialised by hand so it is subscribed before its hat fires (`OnEnable` is not reliably synchronous outside play mode), and the guard stops the two paths both subscribing. This also fixes the wart seen in the first pass's live check, where calling `Initialize` on an already-enabled object doubled every hat — that check measured y = 4 where the program said 2.
- The clone hat is the catalog's first `AllowConcurrent` trigger: ten clones starting are ten independent scripts.
- **Verified:**
  - Compiles clean; **279/279 EditMode tests pass** — 8 new (a clone is a marked copy where the original stands, the original stays active, delete refuses the original, the cap, the clone running its own hat, a clone not re-firing the hat that made it, `Stop` clearing them, and the self-cloning regression). The idempotent-`Initialize` change touches every runner and broke nothing.
  - **In Play mode:** `when Go clicked → repeat 3 { create clone of [me] }` plus `when I start as a clone → change clones by 1 → move forward 2` produced **3 clones**, each at z = 2, with the shared variable reading **3** and the spawner still at 0. `Playback.Stop()` then left **0** clones behind. Before the fix the same program made 1.
- **Not verified:** a real mouse building it, and how 100 clones of a physics-heavy object actually perform (the cap is a guess, not a measurement).

## 2026-09-13 — Workspace anchoring + canvas sizing (the real drop bug)
User screenshot showed two things: the resize strip on the far-left edge, and the canvas content clipped to a thin band at the top of its area.

Needed a dedicated `Vector2Converter` writing only x/y. Worth remembering for any other Unity value type (`Vector3`, `Quaternion`, `Color`) that gets serialized later — likely needs the same treatment.
