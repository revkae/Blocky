# Build Log

Reverse-chronological. One entry per session/milestone step.

## 2026-09-13 — Fix: mirrored, jittering drag ghost; panning clamped to the blocks
User report: "when dragging some mirrored version of it appears and it jitters", plus: panning should stop when the blocks reach the table's edges, so blocks can't get lost — zoom out to see more.

- **Mirrored ghost (likely cause).** The per-frame poll added in the previous entry converted the Input System mouse position with `RuntimePanelUtils.ScreenToPanel` directly. Input System positions are bottom-left-origin; `ScreenToPanel` takes top-left-origin screen coordinates (Unity's own usage flips with `Screen.height - y` first). Unflipped, the polled position was vertically mirrored, and since UI events kept supplying the correct one, the ghost was pulled between the two every frame — a mirrored copy that jitters. Not confirmed by eval (the Editor bridge was down); inferred from the exact symptom and the API's expected input. Fix: one `ScreenToPanel` helper in `BlockyInGamePanel` with the flip, used by the drag poll and by `IsOverWorkspace`.
- **No double-driving.** Even with matching coordinates, two sources moving the ghost each frame is fragile. Both manipulators now treat UI move events as primary: `Poll` only moves the drag when no UI move event arrived since the previous poll — the case it exists for (a control inside the block captured the pointer).
- **Clamped panning.** `BlockyInGamePanel.ClampPan`: with the content bounds (union of stack layouts, table units) and the viewport size, each axis is clamped so that while the blocks fit they stop at the table's edges (16px margin), and when zoomed in past the table's size you can pan across them but never beyond their far side. Applied on every pan/zoom and re-checked each frame (a delete, a drop near an edge, a resize), except mid-drag — the grabbed stack isn't on the table then. "=" now resets zoom and frames the blocks' top-left instead of a fixed offset.
- **Not compiled or tested yet** — the Unity Editor bridge stopped responding (as it has while Play mode was running). Code-reviewed only; compile + EditMode run pending.

## 2026-09-13 — Fix: drag from a checkbox row, click-to-unselect, responsive top bar
User report (with screenshots): pressing the "condition" text on an `If` block couldn't drag it and ticked the checkbox; a selected block should unselect when clicked again; with a narrow workspace the status text and Go button spilled outside the panel.

- **Checkbox row.** A `Toggle` is clickable across its whole row (label + box), and on press it captures the pointer — so pressing the text ticked the box *and* kept the move events away from the drag. Live `Toggle`s are now `pickingMode = Ignore` (their label already was): only the checkbox square ticks it (its click handler lives on the Toggle, so clicks on the square still bubble to it); a press on the text is a press on the block.
- **Drag driven from the real mouse.** `IActiveDrag.Poll` — `BlockyInGamePanel.Update` feeds the open press/drag the actual pointer position every frame while the button is held (and still `ForceEnd`s it on release). A control inside a block capturing the pointer can no longer stall a drag; pressing on the checkbox and moving drags the block (re-parenting the block releases the box's capture, so it doesn't tick).
- **Click again to unselect.** A click on the already-selected block clears the selection — unless the press was on a control's own box (checkbox, number/text box), so editing a value never unselects its block. Starting a drag always selects.
- **Responsive top bar.** Status label now just "Editing '…'", shrinks with `min-width: 0` and ends in an ellipsis; title and Go don't shrink; the top bar clips. The how-to text moved to a wrapping hint line at the bottom of the table. The palette shrinks (`flex-basis: 250px`, `min-width: 140px`) and the table keeps at least 120px.
- Compiled clean. **Tests not re-run:** the Unity Editor bridge stopped responding right after the compile (as it did earlier while Play mode was running), so the EditMode suite still needs a run — no test-covered code changed (manipulators, panel, USS and a field's picking mode only).

## 2026-09-13 — Fix: dragged block sometimes stuck to the cursor
User report: "sometimes it sticks on my mouse and I can't drop it."

- **Cause.** Drags end on a `PointerUpEvent` heard on the panel root. The scene has no UGUI EventSystem, so UI Toolkit reads input itself and only dispatches pointer events it can deliver into its panel. Releasing the button somewhere the panel doesn't receive input — over the game view, or outside the Game window in the Editor — loses the pointer-up, so the drag never ends; when the pointer comes back over the workspace, move events arrive again and the ghost follows it with the button already up. Not reproduced by automation (Play-mode automation still stalls the player loop) — this is the cause the symptom and the input setup point to.
- **Fix.** The physical button is the ground truth. `IActiveDrag` + `DragContext.ActiveDrag`: both manipulators register themselves for the whole press, and `BlockyInGamePanel.Update` calls `ForceEnd` at the cursor whenever `Mouse.current.leftButton` is up while a drag is still open — which also covers an unknown cause of a missing pointer-up. `PointerCancelEvent` now cancels (blocks go back). A new press is ignored while another drag is open; Delete is ignored while dragging. If applying a drop throws, it's logged and the table is rebuilt from the (restored) program instead of being left half-updated.
- 109/109 EditMode tests.

## 2026-09-13 — Table: grab anywhere, pan/zoom, select + Delete
User feedback after trying the table: blocks couldn't be grabbed by their text or checkbox; dragging past the edge made the panel "bug out"; the table should be infinite with panning and zoom; and a clicked block should show as selected and be deletable with Delete.

- **Grab anywhere.** `CanvasDragManipulator` now hears the press in the TrickleDown phase, before any field inside the block, and no longer refuses presses on param fields. The press isn't consumed, so a plain click still reaches the field; only moving past 4px turns it into a drag. Root cause of "can't hold the text": a number field's label is Unity's drag-to-change-value handle — live field labels now have `pickingMode = Ignore`, making them part of the block's handle. Dropdowns stay plain controls (they open their menu on press).
- **Infinite table.** The canvas `ScrollView` (plus the per-frame `FitCanvasToContent` resize) is gone. The table is a clipped viewport; `ProgramCanvasView` is moved and scaled inside it with `style.translate`/`style.scale` (transform origin top-left). Drag empty space to pan; wheel zooms toward the cursor (0.3×–2.5×); +/−/= buttons in the corner. Positions are no longer clamped to ≥ 0. `ChainDragSession` works in two spaces — world pixels for the pointer and snap points, unscaled table units for what's stored — and scales the ghost to the table's zoom while it's over the table (`DragContext.CanvasZoom`).
- **Select + Delete.** Click a block (or hat) to select it; `ProgramCanvasView` owns the selection and re-finds the block by node id after every rebuild (a drag can move it into another stack). Delete/Backspace — ignored while typing in a field — applies the new `DeleteBlock` command: the block goes alone (a C-block takes its mouth contents), blocks below close up, an emptied loose stack disappears, and deleting a hat keeps its blocks as a loose stack. Clicking empty table clears the selection.
- **Typing bug found on the way.** Number/text fields committed every keystroke, and every commit rebuilds the canvas — destroying the field being typed into. Live fields are now `isDelayed` (commit on Enter / focus loss).
- `ProgramEdits` (internal) holds the snapshot + remove-stack helpers both `DropChain` and `DeleteBlock` use.

**Selection outline — debugging note.** The first version drew the highlight as extra stroke passes after the fill (a dark halo, then a white line, each re-tracing the path). It never appeared. Temporary counters in `BlockShapePainter` proved the painter *did* run with `selected == true`, and a label change proved the Editor captures were current — so the extra passes themselves produced no visible geometry. The shipped version uses the one sequence verified to render — one path, one `Fill()`, one `Stroke()` — and expresses selection through colors only (18% lighter fill, 3px white outline). Verified by capture: the selected C-block is visibly lighter with a white outline; its neighbours unchanged. Counters removed afterwards.

**Verified:** 109/109 EditMode tests (+5 `DeleteBlockTests`, +1 selection-survives-rebuild). Selection rendering verified by capture in the Editor window. **Not verified by automation:** the pan/zoom and grab-anywhere gestures in the running game (Play-mode automation still stalls the player loop) — needs a manual pass.

## 2026-09-13 — The table: free placement, Scratch shapes, proximity snapping
User request: the coding environment should work like a table — put blocks anywhere, no "+ Add Stack" button — and a block's *shape* should say what can connect to it (reference: Scratch's hat, stack, C and cap blocks).

**Data.** A stack with an empty `triggerBlockType` is a *loose stack*: blocks lying on the table (`ProgramQuery.IsLoose`). Saved like any stack; the compiler validates it but never emits code (entry point −1, no diagnostic), and `ObjectProgramRunner` skips it — both guard *before* `registry.Find`, which throws on a null key. One new command, `DropChain`, covers every drag outcome: sources are a new palette block, a new palette hat, a node plus everything below it (Scratch's grab rule), or a whole stack; targets are `Free` (loose at a position), `Insert` (into a sequence/mouth), `AttachAbove` (onto a loose stack's top — a hat dropped there makes it runnable) or `Discard`. A loose stack emptied by a pick-up is removed; a triggered one survives empty. Undo restores a serializer snapshot, and a throwing `Place` restores it too, so a bad drop never half-applies. `control.repeat_forever` is now `BlockShape.Cap`.

**Shapes.** `BlockOutline` draws the silhouette with `Painter2D` — notch on top, tab underneath (drawn below the element's rect into the next block's notch, which is why sequences have zero margin), hat bump instead of a notch, no tab for a cap, and per C-mouth an inner tab plus a catching notch. Fill comes from a `--blocky-fill` USS custom property per category, so colors stay in stylesheets. New `HatView`; `BlockView` gained mouths/arms ("else")/footer; `StackView` renders loose stacks without a hat. `ProgramCanvasView` has a `tableMode` (live fields, no buttons) and a `Rebuilt` event. Palette items are real prototypes (`BlockPrototype`) with values as static chips (`ParamFieldFactory.CreateChip`).

**Snapping.** `SnapTargetCollector` lists every connection point on the live canvas (under a hat, under each non-cap block, top of each mouth, above each loose stack); `SnapResolver` picks the nearest within 32px, applying the shape rules: a hat chain can only attach above a loose stack; a chain ending in a cap can't go above anything or where blocks already follow. The chosen target's edge glows (`blocky-drop-indicator`).

**Dragging.** `ChainDragSession` is shared by `PaletteDragManipulator` (new block) and the new `CanvasDragManipulator` (existing blocks: grab a block → it and everything under it; grab a hat or the first block of a loose stack → the whole stack; drop on the palette → delete). Both track the pointer on the panel root with TrickleDown instead of pointer capture, because the grabbed elements are re-parented into the drag layer mid-gesture and detaching an element releases its capture.

**Also fixed:** palette blocks with a Choice param defaulted to an empty choice, which fails validation and silently skips the whole stack — `InstantiatePrototype` now defaults to the first option. Dropdown text was light-gray on the white input (theme popup-text color beats inherited color) — explicit USS rule.

**Verified:** 103/103 EditMode tests (+8 `DropChainTests`, +5 `SnapResolverTests`, +1 loose-stack compile, +1 table-mode canvas). Play-mode automation stalled again (frame 543), so in-game layout couldn't be measured; the collected snap targets were checked structurally against SquareWalker's program (all five connection points with correct insert indices). Shapes were verified visually by rendering the same `BlockView`/`HatView` code in the Editor window and capturing it. **Not yet verified:** an actual drag gesture in the running game — needs a manual pass.

**Superseded, not deleted:** `BlockDragManipulator`/`BlockDragController`/`DropCandidateBuilder`/`DropCandidateResolver` (Milestone 5's containment-based drop model) are no longer used by the in-game UI. They still compile and their tests pass; candidates for removal — see [[09 Decisions/Decisions#ADR-010|ADR-010]].

## 2026-09-13 — Workspace anchoring + canvas sizing (the real drop bug)
User screenshot showed two things: the resize strip on the far-left edge, and the canvas content clipped to a thin band at the top of its area.
- **The panel was never right-anchored.** Unity's default `UIDocument` root styling already sets `left: 0`; with `left`, `right` and `width` all set, Yoga keeps `left` + `width` and ignores `right`. So the "right-hand sidebar" rendered on the left all along — which also retroactively explains the original empty-click bug (the old `pointer.x > Screen.width - panelWidth` gate tested the wrong side of the screen). Now explicitly left-anchored (`right: auto`), which is also the Scratch layout (code left, stage right). Resize handle moved to the right edge, sitting in a reserved `padding-right` strip so it doesn't overlap the canvas scrollbar; drag-right now grows the width.
- **Canvas collapsed to ~45px.** `ProgramCanvasView` positions every stack absolutely, so it contributes no layout size — it was only as tall as its single in-flow child, "+ Add Stack". Consequences: stacks were clipped, *and* `PaletteDragManipulator.CommitDrop`'s `_canvasView.worldBound.Contains(pointer)` check was false almost everywhere, silently cancelling drops. **This is the most likely real reason drag-and-drop "didn't work"** — more so than the threshold change in the entry below. Fixed by `BlockyInGamePanel.FitCanvasToContent()`, run each frame while visible: sizes the canvas to at least the scroll viewport and grows it `CanvasMargin` past the furthest stack; only writes a style when the value changes.
- Tab rail redone as Scratch-style dot + label (the old full-color buttons wrapped "Event" into "Eve/nt" at 10px).

## 2026-09-13 — Resizable workspace, real click gating, drag actually visible + snap glow
User feedback after trying the Scratch-style rebuild:
1. Window should be resizable.
2. Clicking empty space inside the workspace was re-selecting a different world object.
3. Dragging a palette block into the canvas showed nothing, and there was no indication of which side would snap.

Fixes:
- **Resizable**: a 6px drag handle on the workspace's left edge (`BlockyInGamePanel.OnResizeDown/Move/Up`), dragging it adjusts `panelWidth` and reapplies `_root.style.width` live. Clamped between `MinPanelWidth` (360) and `Screen.width - MinGameStrip` so there's always some game view left to click objects in.
- **Click-gating bug, root cause**: the old check was `pointer.x > Screen.width - panelWidth` — a fixed-width guess that silently went stale the moment resizing existed, and never actually covered "clicked empty space inside the workspace" correctly to begin with (it only accounted for the panel's outer rectangle by coordinate arithmetic, not real hit-testing). Replaced with `IsOverWorkspace`: convert the pointer to panel space via `RuntimePanelUtils.ScreenToPanel` and ask `_root.ContainsPoint(...)` directly — correct regardless of resizing, DPI scaling, or which part of the workspace (canvas background, palette gutter, tab rail) was clicked.
- **Drag not visible, root cause**: `PaletteDragManipulator` only spawned its ghost after crossing a 4px move threshold (copied from `BlockDragManipulator`, which needs that threshold to distinguish "click an existing block" from "drag it" — a distinction a palette item doesn't have). Removed the threshold entirely for the palette drag: the ghost now appears the instant the pointer goes down, closing whatever combination of timing/threshold conditions was suppressing the visible feedback.
- **Snap glow (new)**: while dragging a statement/C-block definition, `PaletteDragManipulator` now recomputes the best `DropCandidate` on every pointer move (same `DropCandidateBuilder`/`DropCandidateResolver` call `CommitDrop` already made) and shows a glowing yellow bar (`blocky-drop-indicator`) at that exact candidate rect — the same information Scratch communicates by highlighting the neighboring block's edge, just drawn as a standalone highlight strip rather than reaching into that block's own visual state. Hidden for trigger definitions, which don't snap to anything.
- 88/88 EditMode tests re-verified after these changes; `recompile` clean. Still outstanding from the previous entry: no live Play-mode screenshot of an actual drag gesture, since this sandbox's automated harness can't advance the player loop past frame 2 — these fixes are code-reviewed against the concrete bugs described, not yet pixel-confirmed. Please re-test at the keyboard.

- **Two real bugs found and fixed while getting these green** (both worth remembering, not just "tests failed once"):
  1. `VmScheduler` merged newly-`Start`ed threads into the active list at the *end* of `Tick()`, so a thread started before the very first tick call didn't run until the *second* tick — silently contradicted the intuitive reading of "next tick" and broke every test until moved to the top of `Tick()`.
  2. [[09 Decisions/Decisions#ADR-004|ADR-004]]: `BlockShape.Trigger` being enum value 0 meant test `BlockDefinition`s that forgot to set `shape` were silently treated as triggers and skipped by `OpTableBuilder`, producing a null op table entry that turned into a swallowed `NullReferenceException` → quiet `Fail`. Reordered the enum so the default is the loud-failure case.
- Also learned: after `Tick()` returns, a thread's externally-visible state for "still going" is `YieldedFrame` (or `Sleeping`), not `Running` — `Running` only exists transiently *during* a tick's step loop. Worth remembering if writing more scheduler tests or any UI that displays thread status.
