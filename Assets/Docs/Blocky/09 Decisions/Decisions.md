# Decisions

ADR-style log for anything that deviates from, extends, or resolves an open question in [[Welcome|the TDD]].

## ADR-001 — UI Toolkit over UGUI
**Status:** Accepted (carried over from TDD §8.1)
**Why:** Flex layout gives free vertical stacking and cavity auto-resize; UGUI needs `VerticalLayoutGroup` + `ContentSizeFitter` with manual rebuild ordering, which the TDD calls "the single biggest source of block-editor bugs." Same UITK components serve the in-Editor authoring window.
**Revisit if:** blocks must be authored on an in-world/diegetic surface (open question 1 in TDD §15) — UGUI is more mature there.

## ADR-002 — Instruction carries branch entry *and* exit pcs
**Status:** Accepted (extends TDD §6.2's illustrative `Instruction` struct)
**Why:** The TDD's `Instruction` only lists `JumpA`/`JumpB` (branch entry pcs). But `Thread.Frames[]` is documented as holding "loop counters, **branch returns**" — something has to know where a branch's last instruction is so the Runtime can pop back to the owning C-block without re-walking the tree at runtime (which would mean strings/structure lookups post-link, violating §6.2's "after linking, the runtime touches no strings and no dictionaries"). Added `JumpAExit`/`JumpBExit`: the pc immediately after each branch's last instruction, computed once at link time.
**What this doesn't decide:** whether reaching an exit pc means "fall through to next sibling" (If/IfElse) or "jump back to re-evaluate the loop" (Repeat/RepeatUntil/RepeatForever) is still an open, per-op runtime decision for Milestone 3 (`OpResult.Jump` + `Frame` push/pop) — the compiler only supplies the boundaries, not the looping behavior.

## ADR-003 — Compile errors are per-stack, not whole-program
**Status:** Accepted (TDD §10.2 explicit: "Errors block execution of that stack only, not the whole program")
**Why:** `ProgramCompiler.Link` compiles every diagnostic-free stack and marks a failing stack's `StackEntryPoints[i] = -1` instead of throwing. `Validate` now tags every diagnostic with the owning `StackId` so `Link` can group and skip cleanly. A one-bad-stack program still runs everything else — matches "the offending BlockView gets an error state," not a crash.

## ADR-004 — `BlockShape.Statement` is enum value 0, not `Trigger`
**Status:** Accepted
**Why:** Found the hard way while writing Milestone 3 tests: `OpTableBuilder` correctly skips `BlockShape.Trigger` definitions (triggers aren't dispatched by the VM). But with `Trigger = 0` as the first enum value, any `BlockDefinition` where an author forgot to set `shape` silently became "a trigger" and got skipped — the op table entry stayed null, and the VM's own try/catch around `op.Execute` turned the resulting `NullReferenceException` into a quiet `Fail`, not a loud error. Reordered so `Statement` is 0: an unset `shape` now surfaces immediately and loudly as "no IBlockOp bound to executorKey" at `OpTableBuilder.Build` time (which runs once at boot), instead of a silent no-op discovered later.
**How to apply:** Any new `BlockShape`-adjacent enum should default (0) to the "needs an executor" case, not the "skip me" case — fail loud beats fail quiet.

## ADR-005 — `Frame.IsLoop` distinguishes looping frames from one-shot skip frames
**Status:** Accepted (refines [[09 Decisions/Decisions#ADR-002|ADR-002]] and the loop-yield rule, TDD §6.4)
**Why:** `control.if_else` reuses the exact same Frame push/pop mechanism as `control.repeat` — pushing a frame is the only way to redirect a fall-through past the false branch when the true branch is taken (branches are laid out back-to-back in the flat array). But the generic wrap-detection in `VmScheduler.Step` originally force-yielded at *every* frame wrap, per the loop-yield rule. Applied unconditionally, that would silently add a hidden per-frame delay to every `if`/`if_else` with a non-yielding true branch — by far the most common block shape in any real program. Added `Frame.IsLoop`: only loop frames (`repeat`, `repeat_until`, `repeat_forever`) force a yield at wrap; a one-shot `if_else` skip-frame does not.
**How to apply:** Any future C-block whose branch is taken at most once per entry (not re-entered) should push its frame with `isLoop: false`.

## ADR-006 — RestartOnRetrigger kills and restarts, doesn't reset pc in place
**Status:** Accepted (simplifies TDD §6.4's literal wording)
**Why:** The TDD says a re-fired trigger "resets the existing thread's pc to the entry point and bumps Generation" — implying in-place reuse of the same `VmThread` object. `ObjectProgramRunner.Fire` instead marks the old thread `Done` and calls `scheduler.Start` fresh. Behaviorally equivalent for v1 (no thread pooling exists yet, so there's no allocation cost difference to avoid), and `Generation`-based cancellation only matters once the async adapter (TDD §6.6) exists — neither is built yet.
**Revisit when:** Milestone 7's thread pooling lands — at that point in-place pc reset becomes the actual cheaper path and this should change.

## ADR-007 — `ObjectProgramRunner.Initialize()`/`Shutdown()` are public, not implicit via `OnEnable`/`OnDisable` alone
**Status:** Accepted
**Why:** `GameObject.SetActive(true)` inside an EditMode test did not reliably invoke `OnEnable` synchronously within the test runner. Rather than fight edit-mode lifecycle timing, `OnEnable`/`OnDisable` now just forward to public `Initialize()`/`Shutdown()`, which tests call directly. Production behavior is unchanged; the seam only removes a testing dependency on Unity's own timing.

## ADR-008 — `ChangeColorOp` uses `renderer.material` (instances it), not a `MaterialPropertyBlock`
**Status:** Accepted for now, flagged for revisit
**Why:** `renderer.material.color = ...` is the simplest correct way to change one object's color without affecting others sharing the same material asset, but it silently creates a per-renderer material instance the first time it's touched — extra memory, and it defeats GPU instancing/batching for that object. `MaterialPropertyBlock` avoids both but is more code and was not warranted before real profiling data exists.
**Revisit when:** the Milestone 7 `ProfilerMarker`s (or the Memory Profiler) actually show this mattering for a real scene — TDD §11.2's zero-allocation goal is about the VM's steady-state hot path, not necessarily every visual op, but this is exactly the kind of thing worth checking once there's something to measure.

## ADR-009 — Stopped at Milestone 7; Milestone 8 is post-v1, not started
**Status:** Superseded on 2026-09-18 — the scoping conversation this asked for happened: the user asked for "most stuff that exists in scratch and delightex", which is the product decision to build past v1. Expression blocks ([[09 Decisions/Decisions#ADR-021|ADR-021]]) and variables ([[09 Decisions/Decisions#ADR-023|ADR-023]]) are built; custom procedures and lists are not. The reasoning below is kept because it is still the right rule for *speculative* scope.
**Original status:** Accepted (user decision, 2026-09-13)
**Why:** TDD §13's build order lists Milestone 8 as "Deferred features, in dependency order: undo UI → variables → expression blocks → custom procedures" — read in isolation, this looks like the next thing to build. But TDD §1.2 (Goals, Non-goals for v1) explicitly lists all four of those as v1 non-goals: "Variables and lists," "Custom procedures," "Expression (reporter) blocks," and "Undo/redo UI (plumbing is built in v1, stack is disabled)." The two sections describe the same items from different angles — §13 is a forward-looking roadmap note, §1.2 is the actual v1 scope boundary. Milestones 1–7 satisfy every stated v1 goal; starting Milestone 8 would mean building past what the document itself calls v1, without a real product decision to do so having been made yet.
**How to apply:** Do not start Milestone 8 work speculatively. If the user (or a future planning pass) decides the project needs it, that's a new scoping conversation — likely starting with just the undo/redo UI (cheapest, plumbing already exists), not all four items at once.

## ADR-010 — Loose stacks and proximity snapping replace the containment drop model (in-game)
**Status:** Accepted (user request, 2026-09-13)
**Why:** The user wants the canvas to behave like a table — blocks can lie anywhere, and a block's shape tells you what it connects to. That needs two things the TDD's model didn't have:
1. **Loose stacks.** The data model only had trigger-headed stacks, so a block dropped on empty canvas had nowhere to live (the previous drop was a silent no-op). A `BlockStack` with an empty `triggerBlockType` is now legal: saved, validated, never compiled or run. Chosen over a separate "loose blocks" collection because every existing command, query and view already works per stack; `ProgramQuery.IsLoose` is the only new concept.
2. **Proximity snapping.** Milestone 5's `DropCandidateResolver` picks the drop target by *pointer containment* inside thin gap rects — precise, but not what Scratch does or what the user described ("when it gets close to another block … that side should glow"). `SnapResolver` instead compares the dragged chain's connectors (top-left, bottom-left) with every connector on the table and takes the nearest within a radius, with the shape rules encoded explicitly (hat: bottom only; cap: top only, and only where nothing follows).

Every drag produces exactly one `DropChain` command (TDD §8.3's one-command-per-drag still holds). Its undo is a snapshot restore rather than a step-by-step inverse, since a single drop can edit two containers and add or remove stacks.
**Consequence:** `BlockDragManipulator`, `BlockDragController`, `DropCandidateBuilder` and `DropCandidateResolver` are no longer used by the in-game UI. They still compile and their tests pass. **Revisit:** delete them, or port the Editor window to the table model, whichever comes first — keeping two drag models long-term is a maintenance trap.

## ADR-011 — Conditions are blocks in `Reporter` params, evaluated live through a separate op table
**Context:** `if` / `if else` / `repeat until` took a checkbox (`ParamKind.Bool`) — a literal fixed at compile time, so `repeat until` could never end and nothing could react to input. The user asked for Scratch's hexagonal condition blocks (`mouse down?`, `mouse up?`, `true`, `false`) that drop into a matching hexagonal slot, with a dropdown when the empty slot is clicked.

**Decision:**
- **Data:** a condition is a `BlockNode` stored in `BlockParam.reporter` (`kind = Reporter`) — the slot the schema reserved for exactly this. No schema change. A condition lying on the table is a loose stack whose only block is that condition. `DropChain` gained a `FromConditionSlot` source and an `IntoConditionSlot` target (a filled slot swaps: the old condition pops out as a loose stack); `DeleteBlock` empties a slot; `ProgramQuery.FindNode` also searches slots.
- **Shape:** `BlockShape.Boolean` (appended, value 4) and `BlockCategory.Conditions` (appended, value 4) — appended so existing assets' serialized numbers keep their meaning. The hexagon has no notch or tab, so the silhouette itself says "doesn't stack, goes inside".
- **Compile:** a filled slot becomes `ParamValue.Reporter(opcode, paramOffset, paramCount)`; the condition's own params are appended after its owner's contiguous run, so nesting never breaks an instruction's param range. An empty slot is `EmptyReporter` (false, like Scratch). A condition in a runnable sequence, or a non-condition in a slot, is a compile error.
- **Runtime:** conditions implement `IConditionOp` (not `IBlockOp`) and get their own opcode-indexed table (`OpTableBuilder.BuildConditions`), because they are never scheduled as a step. Ops read condition params with `OpContext.GetBool(i)`, which evaluates the slot *now* — so `repeat until` re-checks every lap.
- **Input:** `BlockyInput.IsMouseDown` excludes presses over the editor (`IsPointerOverUi`, set by `BlockyInGamePanel`), so dragging blocks while a script runs doesn't count as "mouse down" in the game. `mouse up?` is the button *state* (not held), not a one-frame "released" edge.

**Consequences:** old saves still run unchanged: `ProgramUpgrades.UpgradeCheckboxConditions` turns a ticked checkbox into a `true` block and an unticked one into an empty slot, and it runs at every load point (`ObjectProgramRunner.Initialize`, the in-game editor, the Editor window) — so the compiler has no legacy branch and only ever sees the current format. Adding a condition later is one asset plus one `IConditionOp` class. The Editor window's "+ Add" pickers exclude conditions (they don't fit a sequence).

## ADR-012 — Learning aids: scene-wide playback in the scheduler, Reset from a start snapshot, friendly advice in the compiler layer
**Status:** Accepted (user request, 2026-09-14)
**Context:** Thinking as a teacher with no coding background, the user asked for five things so children can see *why* a program goes wrong and get back quickly: a Reset that puts every object back, the running block lighting up, a speed slider plus a one-step button, Undo, and friendly messages ("This script has no ▶ block on top, so it won't start").

**Decision:**
- **Playback lives in `VmScheduler`, not in each runner or op.** One pause/step/speed state that every script in the scene obeys together, like Scratch's stage. `Pause` stops the scheduler's clock too (`_now` doesn't advance), so a half-done wait or timed move resumes exactly where it was. `TimeScale` multiplies `dt`. Everything stays `dt`-driven, so runs remain deterministic.
- **What "one step" means:** each live script finishes or starts **exactly one block**, then freezes, across as many ticks as that block needs. A script caught mid-block (a timed move, a wait) just finishes it. Implemented with a per-thread budget: `VmThread.ResumePc` tells a continuing block (last result `Retry`) apart from a new one, and a thread with no budget left *parks* at the start of its next block. A C-block's lap check counts as a block, so stepping through `repeat` visibly returns to the top each lap. That's deliberate: it's how the loop really runs.
- ~~**Slow motion also lingers.**~~ *Replaced by [[#ADR-013 — Step back from snapshots; speed is 1x–4x; Pause only while running|ADR-013]]: the speed slider became 1x–4x buttons, and `BlockLinger` was removed.* (It used to rest a thread 0.15 script-seconds after each instant block below full speed, so the block stayed lit.)
- **Which block is running:** `VmThread.ActivePc` (the pc of the block started most recently), mapped back to the node through the existing `Instruction.SourceNodeId` → `DebugNodeIds`. `RunningBlocks.Collect` fills a caller-owned list, so the per-frame poll allocates nothing, and the panel only touches the table when the set changes. Drawn by the outline painter in its single Fill→Stroke pass as a thick yellow stroke (`BlockOutline.RunningClass`).
- **Reset = `WorldSnapshot`**, recorded by each `ObjectProgramRunner` on its first `Initialize` (idempotent, so hot reloads don't move the start point). It covers objects given a runner mid-game too. It records exactly what blocks can change: local transform, active, renderer enabled, shared material (undoes `change color`'s per-object copy, ADR-008), and a Rigidbody's pose and velocity. **A new block that changes anything else must extend it.**
- **Go after Reset replays the scene:** `ResetWorld` re-arms `when Play clicked` (`TriggerBroker.ResetPlaySession`). `Go` fires it (a no-op unless re-armed) plus `when Go clicked`, and un-pauses. Step with nothing running first starts what Go would, so Reset → Step walks a program from its first block.
- **Undo UI turned on** (this is the "new scoping conversation" [[#ADR-009 — Stopped at Milestone 7; Milestone 8 is post-v1, not started|ADR-009]] asked for, for undo only): `UndoCapacity = 50` per object in the in-game editor, an Undo button and Ctrl/Cmd+Z (ignored while typing, so text boxes keep their own undo). History is per selected object and starts when it's picked. No redo yet.
- **Friendly advice is `ProgramAdvice` in Blocky.Compiler**, next to the validator it complements, and unit-testable without UI. `Hint` = legal but probably not what was meant (loose blocks, empty event, empty C-block, empty ⬡ hole). `Problem` = the script won't run (number out of range, bad choice, missing value, unknown block). A catch-all turns any compiler error no rule explains into a general message, so a script never fails silently. Messages use the names printed on the blocks. Shown as rows under the table (click selects the block) and as a "!" / "?" badge on the block.

**Consequences:** `VmScheduler` now drops finished threads each tick (they used to accumulate forever), so the running-block poll and step checks stay proportional to live scripts. The Go button moved from the title bar into the run bar.

## ADR-013 — Step back from snapshots; speed is 1x–4x; Pause only while running
**Status:** Accepted (user request, 2026-09-14). Amends [[#ADR-012 — Learning aids: scene-wide playback in the scheduler, Reset from a start snapshot, friendly advice in the compiler layer|ADR-012]].
**Context:** After trying the first version, the user asked for three changes: Pause/Resume only visible once Go has been pressed and something is running; Step forward *and* Step back, to go back and forth; speed as 1x 2x 3x 4x instead of a slider.

**Decision:**
- **Step back restores snapshots; it doesn't replay.** Replaying from the start (Reset, then silently re-run N−1 steps) only works if everything is deterministic. Collisions come from Unity physics and key presses and mouse conditions come from the player, so a replay can diverge from what happened. Instead `Playback.StepForward` records a moment first:
  - every script's progress: `VmScheduler.SaveMoment` → `ThreadMoment` per thread, holding pc, frames, scratch, state and wake time, plus the script clock
  - every programmed object: `WorldSnapshot.SaveMoment`, holding transform, active, renderer, material, color and body motion
  - whether "when Play clicked" had fired yet

  `StepBack` restores the last moment and stays paused. Up to 200 moments are kept.
- **Restore writes into the same `VmThread` objects** rather than making new ones, and brings back scripts that finished since. For that to be safe, `ObjectProgramRunner` no longer keeps its own stack → thread dictionary; it asks `VmScheduler.FindLive(target, program, entryPc)`. Otherwise a restored thread would be invisible to its runner, and a retrigger could run the same stack twice. (Bonus: `Shutdown` now uses `StopWhere`, so it also stops `AllowConcurrent` threads, which the old dictionary never tracked, as its doc always claimed.)
- **Colors are restored only on a material copy.** `change color` recolors a per-object copy (ADR-008). A moment records the material and its color. Restoring recolors a material only if it isn't the object's original, because in the Editor that original is the project asset and writing to it would change the asset on disk.
- **The history covers steps taken since pausing, and is forgotten** on Resume, Go, Stop, Reset and any program edit. Once time runs on or the program changes, the saved moments no longer lead to what's on screen, and after an edit they'd hold threads of the old compiled program.
- **Step forward is ignored while a step is still finishing** (a timed block or a wait), so every saved moment is a clean stop between blocks. The button is disabled meanwhile.
- **Speed is 1x–4x** (`Playback.SetSpeed` → `VmScheduler.TimeScale`). Speeding up only affects blocks that take time. Slow motion is gone, and with it `BlockLinger`; Step is the way to watch instant blocks one at a time.
- **Pause/Resume shows only while something is running** (`Playback.IsRunning` = the scheduler has work), labelled Resume while paused. Step back is disabled when there's nothing to go back to.
- **Stop re-arms "when Play clicked"** (found in the live check). After Stop, Step ▶ started nothing: most demo scripts are "when Play clicked", which fires once per session, and only Reset re-armed it, so Go and Step ▶ silently did nothing after Stop. Now Stop re-arms it too: after Stop, Go or Step ▶ runs every script again from wherever the objects are. Reset additionally puts the objects back.

**Consequences:** the run bar's commands moved from static `BlockyRuntime` methods into the `Playback` class (`BlockyRuntime.Playback`), which can be tested with injected fixtures. Known limit: physics contacts and "looked at" state aren't part of a moment, and a loop with an instant body still runs one lap per frame at any speed.

## ADR-014 — Pause only after Go; Step/Go restart a finished scene; multi-select moves groups loose; the left button selects, the right button pans
**Status:** Accepted (user request, 2026-09-16). Amends [[#ADR-013 — Step back from snapshots; speed is 1x–4x; Pause only while running|ADR-013]] and [[#ADR-010 — Loose stacks and proximity snapping replace the containment drop model (in-game)|ADR-010]].
**Context:** The user asked for six things: Pause only after pressing Go; a working Step; Shift+click to select several blocks and move them together; a selection box dragged over empty table; a resizable palette; slimmer scrollbars.

**Decision:**
- **Pause follows Go, not "something is running".** The demo's "when Play clicked" scripts start by themselves at scene load, so ADR-013's rule (`IsRunning`) showed Pause before the user pressed anything. `Playback.IsGoing` is true after `Go` until the scripts finish, and false after Stop or Reset. A run started by Step doesn't count. It clears itself once the scheduler has no work, so a script a key starts later doesn't bring Pause back.
- **Step and Go restart a finished scene.** Reproduced live: once the demo script ran to its end, Step ▶ paused the scene and saved a step, but started nothing. "when Play clicked" fires once per session, and only Stop and Reset re-armed it. Now both Step and Go re-arm it whenever nothing is running (never started, finished, stopped, or stopped by an edit). Step with no script to start at all does nothing, rather than freezing the scene for nothing.
- **`BlockyRuntime` resets at the start of every Play session** (found during the live check). The project's Enter Play Mode Options disable domain reload, and nothing reset the runtime's statics. So a Pause or Step in one Play session carried into the next: the scheduler started paused (new scripts sat in its pending list forever), "when Play clicked" counted as already fired, and the step history pointed at objects from the previous session. Go and Step then appeared to do nothing, from the very first frame. `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]` calls `BlockyRuntime.Reset()` before any scene object wakes.
- **Selection is a list of `BlockRef`s** (Blocky.Data: stack id + node id, null = hat; equal by node id, so a ref stays valid after its block moves to another stack). `ProgramCanvasView` keeps the list through rebuilds, like the single selection before. `SelectedStackId`/`SelectedNodeId` now name the most recently picked block.
- **A group moves by one command.** `MoveBlocks` runs one `DropChain` pick-up per piece under one snapshot (`DropChain.Execute`, split out of `Do`), so the table rebuilds, saves and hot-reloads once, and one Undo takes back the whole move. `MoveBlocks.Outermost` drops blocks another selected block already carries (a block under a selected hat, further down the same sequence, inside a selected C-block's mouth, a condition in a selected block's slot). Without that, the same nodes would be picked up twice. `DeleteBlocks` deletes each block as `DeleteBlock` would, skipping ones already gone with an earlier one.
- **Groups land loose; they don't snap.** A single chain has one top edge and one bottom edge to connect by; a group has none. Every piece moves by the same distance and lands where it was dropped. Dragging a single block still snaps as before.
- **Left-drag on empty table selects; right or middle drag pans.** The user asked for "click on empty space and drag to choose multiple", which was the pan gesture. Pan moved to the right or middle button. The wheel still zooms, and a plain left click on empty table still clears the selection. The box selects every block it *touches* (hats, blocks, conditions). Shift or Ctrl adds to what was selected.
- **The palette is resized by a seam** (`blocky-ingame-palette-handle`) between it and the table, clamped to at least 140px and to keep the table at least 120px. It sets the palette's `flex-basis`, so a narrow workspace can still shrink it.
- **Slim scrollbars by USS only**, scoped to `.blocky-ingame-root`: 8px track, 6px rounded thumb, no arrow buttons. The palette hides its horizontal scroller.

**Consequences:** the how-to line under the table now teaches the new gestures. The Editor window still selects one block at a time (it doesn't use the table's manipulators). A group can't be snapped onto a stack in one move: drop it, then drag the block you want to connect.

## ADR-015 — Step forward starts every script, whatever hat it has
**Status:** Accepted (user request, 2026-09-16). Amends [[#ADR-014 — Pause only after Go; Step/Go restart a finished scene; multi-select moves groups loose; the left button selects, the right button pans|ADR-014]].
**Context:** "Step still not working — when I press step it should play these blocks connected to event play one by one. All events, not just when play clicked."

**The bug, reproduced live.** ADR-014 made Step start the scripts *when nothing at all was running*: `if (!_scheduler.HasWork)`. The demo scene has SpinnerCube's `repeat forever`, which never finishes — so the scene is never idle, the branch never ran, and every Step press advanced that one spinner and nothing else. A script under any other hat (`when key pressed`, `when collided`, `when looked at`) could never be stepped at all, because between steps the scene is frozen: the learner cannot press the key, cause the bump or look at the object that the hat waits for.

**Decision:**
- **A new hat-independent trigger channel, `TriggerBroker.OnStepAll`.** Every compiled, non-loose stack subscribes to it in `ObjectProgramRunner.SubscribeTriggers`, alongside its own hat's channel. `Playback.StepForward` fires it on every press.
- **The unit is the script, not the scene.** Each press advances every running script by one block *and* starts every script that isn't running. A script that has finished starts again from its first block on the next press.
- **Stepping ignores `RetriggerPolicy`.** `ObjectProgramRunner.FireForStep` starts a stack only if `VmScheduler.FindLive` finds no thread for it. All five event hats are `RestartOnRetrigger`; restarting a script the learner is half way through walking would be the opposite of stepping.
- **`FirePlayClicked` still runs on each Step press** (it is a no-op once fired). It keeps the once-per-session flag honest, so a later Go doesn't restart the scripts Step already started, and Step back can re-arm it. `FireGoClicked` was dropped from Step — `OnStepAll` covers "when Go clicked" stacks without restarting a running one.
- **Go is unchanged.** Go stays the green flag: Play + Go hats only. Starting a "when collided" script without a collision is a debugging act, not a run.

**Consequences:** stepping can run a script whose trigger never happened — deliberate, and what "walk through my program" means for a learner. The tips list under the table says so. Step back still restores every script and object (verified live across a multi-script step).

## ADR-016 — One dark band, light surfaces, and design tokens for the workspace chrome
**Status:** Accepted (user request, 2026-09-16: "search for all these type of apps like code blocks and make this one beautiful editor, make it clean"). Supersedes the chrome half of [[#ADR-012 — Learning aids: scene-wide playback in the scheduler, Reset from a start snapshot, friendly advice in the compiler layer|ADR-012]].
**Context:** The old chrome stacked three different dark slates (title bar, run bar, tab rail) before any content, and the how-to line was a single 30-word sentence of `·`-separated clauses.

**Decision — the rule taken from Scratch 3, Blockly and MakeCode:** one dark band, then light surfaces, so the only saturated color on screen is the blocks themselves (plus green Go and red Stop).
- **Tokens, not literals.** `blocky-ingame.uss` opens with a `:root` block of `--bk-*` custom properties (surfaces, ink, lines, accent, go/stop/warn). Every rule reads from them, so the workspace can be re-themed in one place. The block colors stay where they were, in `blocky-base.uss` / `blocky-*.uss`.
- **Header:** a wordmark tile, and what's being edited as a pill with a dot that lights green — a state, not a sentence — with the toggle key drawn as a key cap at the far end.
- **Run bar:** white, one hairline under it. Go / Stop / Reset in one recessed tray, Pause / Step ◀ / Step ▶ in a second, speed as a segmented control. Paused shows a warm tint plus a "Paused" flag instead of turning the whole bar amber.
- **The table has a dot grid**, painted straight onto the viewport with `Painter2D` (`BlockyInGamePanel.PaintGrid`) and stepped by the pan and zoom, so moving around feels like moving over a surface. One path, one `Fill` — the same single-pass rule `BlockOutline` follows — and the dots are 2px squares rather than arcs, so a screenful is a few thousand triangles, not tens of thousands. It sits under the canvas because an element's own painted content draws beneath its children.
- **The how-to sentence became four chips and a "?"** that opens the full list as a card. The rail marks the category you're on; the zoom cluster is one card with a percentage readout.
- **The workspace opens at `ComfortableWidth` (900) when the screen has room.** Measured live: at the scene's serialized 420 the table sat at its 120px floor, with the footer and the zoom cluster overlapping. The seam on the right still resizes it to anything from 360 up.
- **The palette scrolls sideways** (`ScrollerVisibility.Auto`) because the widest prototype is 344px against a 250px column. `SelectCategory` resets the horizontal offset afterwards: `ScrollTo` would otherwise scroll sideways to fit the widest block and leave every block clipped on its left.

**Consequences:** USS has no `box-shadow`, so "floating" is a white surface with a hairline border; no `text-transform`, so the palette's capitals are made in C#. The Editor window (`Blocky/Program Editor`) is unaffected — it doesn't load this sheet.

## ADR-017 — Two workspace modes: the free Scratch table and a strict single column
**Status:** Accepted (user request, 2026-09-17, with a screenshot of Delightex's CoBlocks: "add two modes to this editor, one is scratch like which is current version and other one is more simplified… it only has one place to go, it is strict").

**Context:** A free canvas asks a beginner to hold two things at once — what the program says, and where on an unbounded surface they put it. CoBlocks removes the second: one column, numbered like lines of code, nothing loose, nowhere to lose a block. Both are worth having, for different learners and different lessons.

**Decision:** one editor, two modes (`WorkspaceMode.Free` / `Simple`), switched from a toggle in the title bar. Simple mode is three policies over the same editor, not a second editor:
1. **Where a drop lands.** `SimpleDropPolicy.Fallback` replaces Free mode's "it lies loose where you dropped it": a chain that snapped to nothing joins the end of the script it landed nearest; a hat starts another script (`DropChain` forbids inserting one); a condition dropped outside a hexagonal hole is **refused** and goes back where it came from, because a loose condition has nowhere to be here. `ChainDragSession` calls it instead of `ChainTarget.Free`. Kept pure so it is tested without a panel, a pointer or a layout pass — the drag machinery itself can only be checked by hand.
2. **How stacks are laid out.** `ProgramCanvasView.Mode` switches stacks from absolute at their `canvasPosition` to `Position.Relative`, so they flow down one column, indented past a gutter. The gutter's numbers are ruled behind the blocks by a row layer rebuilt after each layout pass: every `BlockView` and `HatView`, sorted by its y in canvas space — in one column, top-to-bottom order *is* reading order, nested blocks included.
3. **How the surface moves.** No zoom (the controls are hidden and the wheel scrolls instead), no dot grid, pan locked to the vertical axis (`ClampPan` pins x to 0), no selection box, and no multi-selection — Shift+click is ignored, so a group drag can't start either. Empty table scrolls the column with any button.

**The program is never touched by the mode.** Stored `canvasPosition`s are ignored while in a column and still there on the way back, so the same object can be opened either way and switched back and forth mid-session (verified live). A chain that lands Free in Simple mode still gets a position clear of the other scripts, so a program built in a column doesn't open in Free mode with everything stacked at (0, 0).

**Consequences:** the tips line and its card say different things per mode. Deleting, undo, the condition dropdown, advice, the running-block glow and the whole run bar are shared and behave identically. The Editor window (`Blocky/Program Editor`) is unaffected: it has its own `CanvasMode.Buttons` and never sets a workspace mode.

## ADR-018 — The numbered row is the unit of Simple mode: an area to click, and three places to drop
**Status:** Accepted (user request, 2026-09-17, with the CoBlocks screenshot again: "there are numbers showing how many codeblocks there and it shows area of that code block… I can choose code block by clicking the area. Also make it that when I bring new code block I should be able to swap with current one or just place it above or below of that code block. Also add redo button under undo button."). Extends [[#ADR-017 — Two workspace modes: the free Scratch table and a strict single column|ADR-017]].

**Context:** ADR-017 gave the column a gutter with a number per block, drawn as a hairline. The reference does more with the same furniture: each line is a **band across the whole table**, the band is what you click to pick a block, and a selected block tints its entire line the way an editor highlights the line the caret is on. Aiming at a 30px-tall block is a fine-motor task; aiming at its line is not — which is the whole point of the mode.

**Decision — the row is a first-class object (`CanvasRow`), not decoration.**
- **A band per block, the height of that block**, full table width, with the number in a 36px gutter. `ProgramCanvasView.UpdateRows` measures the laid-out `BlockView`/`HatView`s and re-points a pool of bands at them.
- **Reading order comes from sorting `(y ascending, height descending)`.** A block that contains another has the same-or-smaller y and a bigger height, so it sorts first and its band is added first — which puts a nested band *on top* of the band around it, both to click and to paint. The innermost band therefore wins the press, and a selected C-block's tint shows through its transparent children's bands. That is exactly what rows 3 and 4 of the reference do.
- **Clicking a band picks its block** (`Select`), and the press is deliberately *not* stopped, so dragging a band still scrolls the column like the empty space around it. `BlockyInGamePanel.OnViewportPointerDown` skips its usual "empty table clears the selection" when the press landed on a band (`CanvasRow.Of`).
- **Scripts step out of the way of hit-testing in Simple mode** (`StackView.pickingMode = Ignore`). A script stretches the full width of the column, so its empty right-hand side used to swallow every press meant for the band behind it. Nothing needs the script itself as a hit target — each block inside it is picked on its own.
- **Three places per row, chosen by where on it you let go** (`RowTargetResolver`): near the top edge the chain goes in **above**, near the bottom **below**, and in the middle it takes that block's **place**. The edge zone is 30% of a short row but never more than 26px, so a C-block holding half a script doesn't turn most of the table into "above". A snap edge within reach still wins — it is the precise gesture; the row zones are the coarse one, and replace the old "joins the end of the nearest script" only when the pointer is actually over a row.
- **Replace is a new `ChainTargetKind`**, not a delete plus an insert: `DropChain` takes the block out and puts the chain in at the same slot, in one command, so one Ctrl+Z brings the replaced block back. Its nested contents go with it — that is what "swap with this one" means for a C-block, and undo is the safety net.
- **The shape rules are the ones the silhouettes already draw** (`RowTarget.Allows`): nothing goes above or in place of a hat, nothing goes under a cap, and a chain ending in a cap can't be put in front of blocks that follow. An intent the row refuses falls back to one it allows; a row that refuses all three hands the drop back to `SimpleDropPolicy`.
- **Redo, under Undo.** `ProgramStore` grows a redo stack: `Undo` moves the command onto it, `Redo` re-runs `Do` (every command resolves what it touches from the program as it is *now*, and undo has just put that back), and any fresh edit clears it — history has branched. Ctrl+Y and Ctrl+Shift+Z both work; the tools cluster is a column, so Redo sits under Undo.

**Consequences:** the drop indicator gained a caption ("Above" / "Replace" / "Below") and two looks — an accent bar on the line for above/below, the block ringed for replace. The bar is blue rather than the snap glow's yellow because it is drawn along the edge of a warm-colored block. Free mode is untouched: no bands, no row targets, scripts pick normally.

**Fixed on the way:** the bands only ever appeared once. `UpdateRows` ran from the canvas's own `GeometryChangedEvent`, but the canvas is pinned at 100%x100% of the viewport, so its rect never changes — every rebuild (any edit, any undo) wiped the row layer and nothing fired to build it again. The layer and its pooled bands now outlive the rebuild, each stack re-measures the column as it is laid out, and a rebuild schedules one pass for the case where nothing moved at all.

## ADR-019 — A stack ends at its own exit pc, not at the end of the program
**Status:** Accepted (fixes a latent bug found while adding `stop` and `broadcast`)
**Why:** Every stack of an `ObjectProgram` is emitted one after another into a single `CompiledProgram.Code` array, and the only thing that ended a thread was `pc >= Code.Length`. So a script that simply ran out of blocks carried straight on into **the next script's blocks**. It had stayed invisible because the demo objects each had one script, or ended in a `repeat forever`, and no test had ever run two stacks of one program at the same time. The first block that needed exactly that — `stop [other scripts on this object]` — failed immediately, and so did `broadcast` (the sender fell into the listener's body).
**What changed:** `ProgramCompiler.Link` records `StackExitPoints[i] = code.Count` after emitting each stack (-1 where the entry point is -1), `CompiledProgram.ExitPcFor(entryPc)` looks one up, and `VmThread.ExitPc` is read once at construction. `VmScheduler.Step` ends a thread at `pc >= t.ExitPc`. A stack with no blocks at all (entry == exit) is now `Done` at birth instead of running its neighbour.
**How to apply:** anything that computes "where does this script end" must use the stack's own exit, never `Code.Length` — the array belongs to the whole program, not to one script.

## ADR-020 — Catalog breadth first, in Scratch's own categories; value reporters come later
**Status:** Accepted
**Why:** Bringing the catalog toward Scratch/Delightex parity splits cleanly in two. Everything that is *statement- or boolean-shaped* (`and`/`or`/`not`, `key pressed?`, `touching?`, `timer >`, `wait until`, `stop`, `broadcast`, `when I receive`, `when clicked`, `change position`, `glide to`) needs no new architecture at all: one `.asset` plus one `[BlockExecutor]` class each, exactly as TDD §7 promises. Everything else in Scratch — the arithmetic operators, variables, `distance to`, `join`, `say` — needs a **value** reporter: a round slot that answers a number or a string, where today `ParamKind.Reporter` only resolves to an `IConditionOp` returning `bool`. Breadth first costs nothing later, because a reporter dropped into a `Number` param does not change any block authored before it.
**Categories:** `BlockCategory` gained `Sensing`, `Operators`, `Sound` and `Variables` (append-only — assets store the number). The four original `condition.*` blocks moved into their Scratch homes (`mouse down?`/`mouse up?` → Sensing, `true`/`false` → Operators); the `Conditions` member stays in the enum so no serialized value shifts, but no block uses it and the tab rail no longer shows it. Colors follow Scratch: Sensing light blue, Operators green, Sound magenta, Variables orange.
**What this doesn't decide:** how a value reporter is represented (`ParamValue` union vs. a separate table), or whether variables are per-object or scene-wide. Both belong to the reporter phase.

## ADR-021 — Any input can hold a block; a reporter answers a `BlockValue`, not a type
**Status:** Accepted (the second half of [[09 Decisions/Decisions#ADR-020|ADR-020]])
**Why:** Scratch's round blocks are the other half of its language — arithmetic, `pick random`, `join`, variables, `distance to`. None of them fit the old model, where `ParamKind.Reporter` was the only slot that could hold a block and the only thing it could hold was an `IConditionOp` answering `bool`.
**What changed, and the two decisions inside it:**
1. **Any param can be filled by a block, not just a `Reporter` one.** `BlockParam.reporter` was already on every param; the compiler now honours it for `Number`, `Text` and `Bool` inputs too, and every op reads its inputs through `OpContext.GetNumber` / `GetText` / `GetBool` instead of `Params[i].Number`. That single change makes *every white oval in the catalog* accept an expression — including the ones written months ago — without touching a single block asset. A hexagonal hole still takes only conditions; a value oval takes a reporter or a condition (a condition there reads as "true"/"false", as in Scratch).
2. **Values are untyped at the edges.** `BlockValue` carries what it is (number, text, boolean) and converts on demand: text that looks like a number reads as one, anything else reads as 0, and `=` compares two number-ish things numerically and anything else as case-insensitive words. A learner never sees a type error, which is the whole point — Scratch has no visible types, and a block language that refuses `join (1 + 1) "!"` would be teaching the wrong lesson.
**Cost:** two op tables become three (`IBlockOp`, `IConditionOp`, `IValueOp`, all bound from one reflection scan), and `SlotEvaluator`/`SlotContext` became `SlotEvaluator`/`SlotContext` because they now serve both shapes.
**How to apply:** a new op must read inputs through the `Get*` accessors. Reading `ctx.Params[i].Number` directly is now a bug — it silently ignores whatever reporter a learner dropped there. (`ChoiceIndex` is the exception: a dropdown is a fixed list, not a value, and never takes a block.)

## ADR-022 — A block in an input is saved next to the value it covers
**Status:** Accepted
**Why:** `BlockParamConverter` wrote only the union field matching `kind` (TDD §5.1), so a reporter dropped on a *Number* input was thrown away on save: the program ran the literal underneath and the learner's expression vanished. Found in Play mode, not by 25 green unit tests — they build nodes in memory, and only the live run goes through JSON.
**What changed:** `reporter` is written and read for every kind, *and* the literal stays beside it. Keeping both is what lets pulling a reporter back out restore the number that was typed before it landed — the behaviour Scratch has when a block covers a value.
**How to apply:** when a union gains a field that can coexist with the others, the converter's `switch` is the wrong shape for it. Write the shared field outside the switch.

## ADR-023 — Variables are named at the point of use, in one of two scopes
**Status:** Accepted (resolves open question 5, "variable support before first release?")
**Why:** Scratch makes you *create* a variable in a dialog before you can use it, then offers it as a named block. That needs a per-program variable list, an editor for it, and a palette that rebuilds itself — a lot of machinery before a learner can count anything. Blocky names the variable **in the block**: `set [score] to (0)` takes the name as ordinary text. A variable exists because something set it, and reading one that was never set answers empty (0 as a number, "" as text) instead of failing. Names are trimmed and compared case-insensitively, so "Score" and "score " are one variable — a typo is a bug a learner cannot see, and this removes a whole class of them.
**Two scopes, as in Scratch:** one store shared by the whole scene, and one private to each object, chosen by a dropdown on all three blocks (`everyone` / `this object`, read by index). Per-object is what lets ten copies of one program each count their own score. Per-object entries are keyed by `GameObject` and pruned when a destroyed object's key is found, the same trick `BlockCollisionRelay` uses for contacts.
**Values, not strings:** the store holds `BlockValue`, so `set score to 10` keeps a number a number and `>` still compares it numerically afterwards. `change by` reads whatever is there as a number, which is why it works before the variable has ever been set.
**Lifetime:** the store lives on `BlockyRuntime` and is dropped with everything else at the start of a play session — domain reload is off in this project, so a static that is not reset is a bug waiting to happen.
**What this doesn't decide:** lists (Scratch's other data type), and whether a variable should ever persist between sessions.

## ADR-024 — Variable watchers live on the table, not over the game
**Status:** Accepted, with a known limit
**Why:** Scratch shows a variable's value on the stage, and being able to *see* a number change is most of what makes variables teachable. The game view is not ours to draw on: the panel's root **is** the `UIDocument` root, so anything added to it disappears with the workspace when the learner presses Tab. Rather than restructure the panel's root for this, the watcher card sits in the table's top-left corner — visible exactly when someone is building or debugging a program, which is when the value matters.
**Known limit:** with the workspace closed, the values are invisible. Putting monitors over the game means splitting the document root into a workspace layer and an always-on overlay layer; worth doing, but it is a change to the panel's skeleton and did not belong in the same pass as the blocks.
**Only shared variables are listed:** one row per name, and ten objects each with their own `hits` would be ten rows all claiming to be `hits`.

## ADR-025 — One object names another by its name, resolved through a registry
**Status:** Accepted
**Why:** Half of Delightex's language and a good part of Scratch's is one object talking about another — `distance to`, `point towards`, `go to`, `touching [that]?`. Something has to turn "the Ball" into a `GameObject`. This project already identifies objects by name (`ObjectProgram.targetObjectUid` is a name, and the in-game panel keys saved programs by `go.name`), so an `ObjectRef` input holds a name and nothing new is stamped on the scene.
**The cost that had to be designed around:** `GameObject.Find` is a scene-wide search, and these blocks are read *inside loops* — `repeat forever { point towards [Ball] }` would run one per lap. So `BlockyObjects` is a registry: every `ObjectProgramRunner` registers itself on start and unregisters on shutdown, making the common case a dictionary hit. Anything else is searched once and remembered, and **a miss is remembered for the rest of the frame** — without that, one mistyped name costs a full search every lap forever. Per frame rather than permanently, so an object that appears later is still found; `Register` clears a name's miss immediately.
**Reserved names:** `me` / `myself` / `self` / `this` and an empty input mean the object running the script; `camera` means the main camera. An unknown name resolves to null, and every block treats null as "do nothing" — `distance to` answers 0 rather than something enormous, because a learner who mistypes a name should see nothing happen, not watch an object fly out of the world.
**`point towards` is yaw only:** the direction is flattened onto the ground plane first, so an object told to face something overhead turns the way a person would rather than tipping onto its back. `go to [object] over (duration)` re-reads the target's position every tick, so it follows something still moving instead of gliding to where it used to be.
**What this doesn't decide:** how the editor should *offer* the names (today the input is a text field; a dropdown of scene objects would be better and needs the panel to hand the palette a scene lookup), and what should happen when two objects share a name.

## ADR-026 — Clones are real GameObjects, capped, and never made by deactivating the original
**Status:** Accepted
**Why:** Scratch's clones are how a learner makes bullets, enemies and confetti — one object spawns, the copies do the work. Here a clone is a plain `Instantiate` of the object, so it brings its colliders, its renderer and its `ObjectProgramRunner` with it and needs no special case anywhere in the VM. A `BlockyClone` marker component is the only thing added, and its only job is to let `delete this clone` refuse to delete the original.
**Capped at 100.** Scratch allows 300 sprites' worth; these are real objects with physics, and `repeat forever { create clone }` is a program a learner will write on purpose. Past the cap `create clone` quietly does nothing, which is Scratch's behaviour too — the program should slow down, not take the machine with it. `Stop` deletes every clone, so a run never leaves its copies lying around.
**The thing that had to be learned the hard way:** the first version deactivated the original for the instant of the copy, to keep the clone's scripts quiet until it had been marked and announced. But disabling an object runs `ObjectProgramRunner.OnDisable`, which halts every thread it started — so an object cloning *itself* killed the loop doing the cloning. `repeat 3 { create clone of me }` made exactly one clone, and only Play mode showed it: the unit test cloned once, so a dead thread changed nothing. There is no need for that window at all, because `Instantiate` returns long before the scheduler ticks again.
**`Initialize` is now idempotent** (`Shutdown` clears the flag). A clone is initialised by hand so that it is subscribed before its `when I start as a clone` hat fires — necessary because `OnEnable` is not guaranteed synchronous outside play mode ([[09 Decisions/Decisions#ADR-007|ADR-007]] again) — and the guard means the two paths can never both subscribe. That also fixes a wart from an earlier live check, where calling `Initialize` on an already-enabled object doubled every hat.
**The clone hat is `AllowConcurrent`**, unlike every other trigger: ten clones starting are ten independent scripts, and `RestartOnRetrigger` would have each new clone cancel the last one's script.

## ADR-027 — Say/think bubbles are a TextMesh, not TextMeshPro, and one block covers all four Scratch blocks
**Status:** Accepted
**Why (the font):** TMP is the obvious choice and the wrong one here — it is in the project as a package, but it has **no font assets and no TMP Settings**, so a TMP bubble renders nothing at all and logs "import TMP Essential Resources". Importing those adds megabytes of assets to someone's project as a side effect of adding a block, which is not a decision a block should make. The legacy `TextMesh` with Unity's built-in font needs nothing, and it was checked on screen under URP (`GUI/Text Shader` reports `isSupported`, and the text rendered) *before* the bubble was written rather than after.
**Why one block:** Scratch has four (`say`, `say for n seconds`, `think`, `think for n seconds`). Here `looks.say` takes a message, a seconds value and a style: `seconds = 0` leaves the bubble up until something changes it, anything else shows it and clears it after, and the style dropdown is the difference between saying and thinking. Saying nothing clears the bubble, as an empty `say` does in Scratch. Four blocks' worth of behaviour, one row in the palette — Delightex does the same.
**Details that turned out to matter:**
- The bubble aligns to the **camera's up**, not the world's. With world up it leans a couple of degrees whenever the camera looks down at it, which reads as sloppy rather than as depth.
- It builds itself on first use rather than in `Awake`, because a component added outside play mode never gets an `Awake` — and that is exactly how the tests add one.
- Its backing quad's collider is removed with `DestroyImmediate` outside play mode (the same trap as clones: `Destroy` there only logs an error), so a bubble is never something to bump into.
- `Stop` clears every bubble, like it deletes every clone: a stopped run leaves nothing on screen.

## ADR-028 — Lists: a second store beside variables, same names, same scopes
**Status:** Accepted — built 2026-09-24 (user request: "Custom blocks … and lists"). Compiled and tested outside Unity only (18 `ListTests`); not yet opened in the editor. What changed from the proposal is under **As built** below.
**Why:** Scratch's other data type. In a 3D game it is what a learner reaches for to keep a queue of waypoints, a high-score table, or the colours a light cycles through.
**Shape of it:**
- `BlockyVariables` gains a second dictionary, name → `List<BlockValue>`, with exactly the variable rules: named in the block, trimmed and case-insensitive, shared or per-object by the same `everyone` / `this object` dropdown, and a list that was never touched reads as empty rather than failing.
- **Indices count from 1**, as in Scratch, and an index out of range is a no-op for the statements and empty for the reporters — the same "a typo does nothing, it never throws" rule every other block follows.
- Blocks: `add (thing) to [list]`, `delete (n) of [list]`, `delete all of [list]`, `insert (thing) at (n) of [list]`, `replace item (n) of [list] with (thing)` (statements); `item (n) of [list]`, `item # of (thing) in [list]`, `length of [list]` (round); `[list] contains (thing)?` (hexagon, using `ValueComparison` so "10" matches 10).
- The watcher card lists a shared list as `name  [a, b, c]`, truncated past a few items.
**Cost:** one dictionary, nine ops, nine assets. No VM or editor change — every input is an ordinary value input.
**As built:**
- **Their own category.** In the Variables tab the nine list blocks sorted *before* the three variable blocks (the palette orders a category by `blockType`), which read as a jumble. `BlockCategory.Lists` (appended, value 9) gives them a tab of their own, in Scratch's deeper list orange.
- **Every change makes the list; reading never does.** So `delete all of [items]` — the usual first block of a program that fills one — puts `items  []` on the watcher, while asking the length of a list nobody has used doesn't.
- **A cap of 10,000 items**, for the same reason as the clone cap: `repeat forever { add … }` should stop growing, not use up the machine.
- **Position inputs are 1–10,000**, so a typed 0 is flagged by the advice ("positions count from 1") instead of silently doing nothing; a *computed* position outside the list still does nothing.
- The store keeps one `Store` (values + lists) per scope, so pruning a destroyed object drops both at once.

## ADR-029 — Custom blocks reuse the loop-frame machinery the VM already has
**Status:** Proposed — **not built**, same caveat as ADR-028. This is the design, worked out on paper against the code as it stands.
**Why:** Scratch's "My Blocks" — name a sequence, call it from anywhere, pass it values. The last big piece of Scratch's language.
**The key observation:** a call is already a thing this VM knows how to do. A loop pushes a `Frame { OwnerPc, ExitPc }` and jumps into its body; when the pc reaches `ExitPc`, the scheduler hands control back to `OwnerPc`, and the owning op decides what happens next. A call is the same shape with a different body: push a frame whose `ExitPc` is the **definition stack's own exit** (which [[09 Decisions/Decisions#ADR-019|ADR-019]] made the compiler record), jump to the definition's entry, and when control comes back to the call's pc, pop and carry on. No new instruction kind, no new scheduler path.
**The one VM change it needs:** `VmScheduler.Step` ends a thread at `pc >= t.ExitPc`, and a definition's code lives *outside* the calling stack's range, so its first instruction would end the thread. The bound must become "the exit of the innermost call frame, or the thread's own exit if there is none". That needs `Frame.IsCall` beside `Frame.IsLoop`, and it is the only line of `Step` that changes.
**Arguments:** each call frame gets its own argument values, evaluated at the moment of the call and kept on a small per-thread stack, so recursion works — `argument [x]` inside the definition reads the *innermost* call's value. Recursion depth is capped by the existing `VmThread.MaxNestingDepth` (16) shared with loops; past it the call does nothing, which stops a runaway recursion instead of crashing.
**The honest compromise — fixed inputs:** in Scratch, a call block grows exactly the inputs its definition declares. Here block shapes come from static `BlockDefinition` assets, and a call block whose inputs depend on another stack would need the palette, the compiler and the serializer to understand dynamic shapes. Proposed instead: `define [name]` as a hat, `call [name] with (a) (b) (c)` as a statement with three generic value inputs, and `argument [a|b|c]` as the reporter. Less elegant than Scratch, buildable without touching the editor's shape model, and it can grow into the real thing later without a data change.
**Open:** whether a definition may be called from another object's script (Scratch says no — a custom block belongs to its sprite; the proposal agrees), and what `stop [this script]` should mean inside a definition (Scratch: it ends the whole thread, not just the call — the proposal agrees, since `Done` already does that).

## ADR-030 — Localization on Unity 6.7's built-in runtime, with the words in one JSON file per language
**Status:** Accepted. Built and unit-tested outside Unity (below); **not yet opened in the editor.**
**Why Unity Localization, and why the built-in one:** the project is on Unity 6.7, which ships localization as an engine module (`com.unity.modules.localizationruntime`, already in the manifest). It gives locale selection, per-key fallback to English, Smart String formatting, and a remembered choice (`PlayerPrefLocaleSelector`), with no Addressables — the old `com.unity.localization` package would have added Addressables to the project for the sake of a few hundred strings.
**Why the words are JSON files and not table assets:** Unity's authored route is a String Table Collection edited in the Localization Tables window. Those are editor-made assets, and this change was written with no editor to make them in; hand-writing their YAML would mean guessing engine script ids. Instead `LanguageFileProvider` sits in the settings' asset provider chain — the extension point Unity documents for new table formats — and builds each locale's `ResourceTable` from `Resources/Languages/<code>.json`. Everything after the table (lookup, fallback, formatting, switching) is Unity's. Side benefits: a translation is a readable, diffable file, and **adding a language is adding a file** — nothing lists the languages.
**Keys are derived from stable ids, not from `displayNameKey`.** The TDD calls `displayNameKey` a localization key, but every asset stores its English name there. Rather than rewrite 71 assets, a block's key is `block.<blockType>` (inputs `param.<key>`, choices `choice.<paramKey>.<stableId>`), and `displayNameKey` stays as the English fallback — so a block nobody has translated yet, or a failure to start localization, still shows English, never a key.
**Advice is whole sentences.** Messages that used to be glued from fragments ("…, like the one in X") are separate complete strings with placeholders, because Turkish puts the names elsewhere in the sentence.
**Choices keep their ids.** Dropdowns now list the stable ids with a formatter that shows their translated names, so what a program stores never depends on the language it was written in.
**Verified (outside Unity):** the Localization, Compiler and Data sources and their tests compile at C# 9 against stubs whose signatures were copied from UnityCsReference `6000.7.0a6`; with those stubs turned into small fakes ported from the module's own lookup and fallback code, all 45 Compiler + Localization tests pass, including every English advice assertion with English pinned, and Turkish lookups, capitals and advice. That check caught one real bug: in 6.7 `ISynchronousAssetProvider` does not extend `IAssetProvider`, so the provider must implement both. **Not verified:** the Editor/Game assemblies (UI Toolkit) were reviewed but not compiled, and nothing has run inside Unity — Smart String formatting, the language buttons' look in the header, and the in-place redraw need a look in Play mode.
**The switch is plain buttons, not Unity's `LanguageDropdown`.** The first version used the module's dropdown; it was a small pill that hid itself with fewer than two languages and was easy to miss. One button per language, styled as the Free / Simple toggle, is always there and says what it does.
**Revisit if:** translators want Unity's Tables window. A String Table Collection named `Blocky` added in the editor sits ahead of or beside the provider without code changes; the JSON files could then be imported once and retired.

## ADR-031 — In-game saves: keyed by scene and hierarchy path, run at startup, never overwritten when unreadable
**Status:** Accepted (user request, 2026-09-24: "Fix what is known to be wrong", [[11 Release/Release Readiness|Release Readiness]] §2). Built and tested outside Unity only; not yet opened in the editor.
**Context:** the in-game editor saved each object's program to `BlockyPrograms/<object name>.json`, and only the editor ever read it back. So after a restart every object ran its *scene* program while the editor, once opened, showed the student's — what you saw was not what ran — and an object first programmed in the game (the editor adds its runner at runtime) ran nothing at all. The name alone as a key also let same-named objects, in one scene or across scenes, share a file; a name with `/`, `:` or `?` could not be saved on Windows; and a damaged or newer-version file threw inside the editor.
**Decision:**
- **Key = scene / hierarchy path**, one file per object at `BlockyPrograms/<scene>/<parent>/…/<object>.json`, with `[n]` after an object that has n earlier siblings of the same name. Names compare case-insensitively (as Windows and macOS disks do), and every part goes through `RuntimeProgramStorage.SafeName`: characters some file system refuses — plus `%`, `[` and `]`, which the key uses itself — become `%XX`; a trailing dot or space is escaped; Windows device names (`CON`, `COM1`…) get their first letter escaped; very long names are cut and end in a stable FNV hash. The mapping never loses information, so two different objects never share a file.
- **Not a GUID component.** A serialized id would survive renames, but every programmable object would have to carry it, objects programmed in the game have none, and duplicating an object in the editor copies it. The path is readable in the saves folder — a teacher can find `BlockyDemo/SquareWalker.json` — and needs nothing on the objects. **Cost:** renaming or moving an object in the Unity Editor gives it a new key, so it starts again from its scene program; the old file stays on disk.
- **The runner runs the save.** On its first `Initialize` (or `LoadProgram`), `ObjectProgramRunner` looks for a save under its key and, when there is one, makes it its program asset — so a clone made later copies the asset and runs the same program, and the in-game editor, opening the object, reads `LoadProgram()` and shows exactly what runs. `BlockyRuntimeTicker.Awake` gives a runner back to every object that has a save but no runner. **Precedence:** a program handed over by code (`SetProgramAsset` — the editor's hot reload, the tests, the Editor window) wins over a save; a save wins over the scene's program.
- **Unreadable files are set aside, never overwritten.** `TryLoad` renames a file it can't use to `<file>.<time>.unreadable` (or copies it, if it can't be moved), logs where it went, and the object runs its scene program; the in-game editor says so above the advice. `TrySave` never throws: a failed save keeps the edit running and says so, and the next good save clears the note.
- **`Blocky > In-Game Saves`** (Editor menu) shows the folder and deletes it, because a save now wins over the scene's program in the Editor's Play mode too — without it, an edit made in the Unity Editor would seem not to run.
**Not done here:** named projects, export/import, per-student saves and "reset to the original" are classroom features ([[11 Release/Release Readiness|Release Readiness]] §4). Old saves under the previous `DefaultCompany` folder are not migrated: they were test data, never shipped, and never loaded at startup.

## ADR-032 — The statics-cleanup analyzer is answered per file, not with its attribute
**Status:** Accepted (2026-09-24, [[11 Release/Release Readiness|Release Readiness]] §2).
**Context:** Unity's statics-cleanup analyzer warns `UAL0010` / `UAL0013` on any type with static fields, automatic properties or events that lacks `[AutoStaticsCleanup]` or `[NoAutoStaticsCleanup]` (`Unity.Scripting.LifecycleManagement`). The Asset Store wants packages that compile without warnings. Those attributes only exist in recent Unity 6 releases — they break the compile on 6.0 LTS — and using them here would also need an assembly reference that older versions don't have, which ties Blocky to 6.7 exactly when §3 of Release Readiness may make it run on 6.3 LTS.
**Decision:** every non-test file that declares static state starts with `#pragma warning disable UAL0010, UAL0013` and one line saying why nothing more is needed — either "Blocky resets these statics itself at the start of every Play session" ([[#ADR-014 — Pause only after Go; Step/Go restart a finished scene; multi-select moves groups loose; the left button selects, the right button pans|ADR-014]]'s `SubsystemRegistration` rule), or "fixed values" / "caches" that are the same in every session. A pragma with an unknown id is ignored by older compilers, so this is quiet on every Unity version. `BlockyInput`, whose statics were the one set not reset per session, now is.
**How to apply:** new static state still needs its reset at `SubsystemRegistration` — the pragma quiets the analyzer, it does not do the reset. When the minimum Unity version has the attributes, `[NoAutoStaticsCleanup]` on these types says the same thing more precisely.
